# レビュー・修正ワークフロー

## 適用範囲と許可

- 親agentが調整し、レビューはGPT-6 Astraのウルトラ、修正はGPT-6.1 Solの高に担当させる。親が指定モデルの作業を代行しない。
- ユーザーが「レビューして」などの依頼をした場合、その対象に限り修正・コミット・プッシュまでの明示許可を含む。「`$review`で対象をレビュー」のように対象を伴ってこのスキルでの作業を明示的に依頼した場合も含め、「一括」という追加の語句の有無だけで再確認しない。PRは作成しない。得た許可を再確認しない。
- 自動選択は可能だが、自動選択だけ、名前への単なる言及、手順の説明、このスキルの作成・更新依頼は外部操作の許可にしない。その場合は許可済みの作業を進め、未許可の操作が必要になった時点で下記の確認方法を使う。
- 無関係な既存変更・コミットを取り込んだり送信したりしない。履歴書き換え、force push、PRのマージは含まない。

## 対象と比較基準

1. ブランチ指定がなければ現在のブランチを対象にし、指定があればそれを尊重する。`main`も勝手に別ブランチへ変えない。未コミット変更で安全な切り替えができない場合やdetached HEADの場合は確認する。
2. 対象リポジトリの`AGENTS.md`、仕様、検証方法、Git状態、リモートを確認する。参照可能な同サービスの`{{サービス名}}_docs`と関連領域の実装も確認する。
3. 開始時のHEAD、ステージ済み・未ステージ・未追跡ファイルとその内容を記録し、既存のユーザー変更を保護する。勝手なreset、clean、stash、ステージ解除や既存変更の上書きをしない。
4. 比較先はユーザー指定を優先する。指定がなければ既存PRのマージ先、なければリモートのデフォルトブランチを調べ、取得した比較先と対象ブランチのmerge-baseのSHAを固定する。比較先・対象範囲が不明な場合や、現在の`main`のコミット済み変更をどこから見るべきか不明な場合は確認する。反復中にbaseを動かさない。
5. レビュー対象は固定baseからHEADまでのコミット済み変更、ステージ済み変更、未ステージ変更、未追跡ファイルの全体とする。削除・名前変更も確認する。`git diff <固定base>`に含まれない未追跡ファイルは、`git ls-files --others --exclude-standard`等で列挙して内容を確認する。既存のユーザー変更も文脈から除外しないが、修正・送信の許可は別に扱う。

## 独立レビュー

初回を含む各回で、`collaboration.spawn_agent`に次の値を指定して新しいレビュアーを作る。`task_name`は回ごとに変える。

```text
task_name: review_round_1
model: gpt-6-astra
reasoning_effort: ultra
fork_turns: none
```

`message`には依頼内容、対象リポジトリの絶対パス、適用指示・関連仕様、ブランチ、固定base SHA、全差分の確認方法、検証方法、確認済みの回答を明示する。前回レビューの結論や修正者の「解決済み」判断は渡さず、最新の実装と差分から独立して判定させる。

レビューは読み取り専用とする。仕様違反や具体的な不具合について、重要度、ファイルパスと行、再現条件・根拠、必要な検証を報告させる。好みだけの指摘を不具合に数えない。指摘がない場合も、確認範囲と検証結果・未実施事項を明示させる。

## 同一agentによる修正と反復

1. 修正が必要になった最初の時点で、`collaboration.spawn_agent`に`task_name: review_fixer`、`model: gpt-6.1-sol`、`reasoning_effort: high`、`fork_turns: none`を指定する。返されたagent IDを最後まで保持する。
2. `message`には依頼、絶対パス、適用指示・仕様、ブランチ、固定base SHA、開始時の変更と保護対象、指摘と根拠、検証方法、確認済みの回答を明示する。履歴は引き継がれないため、必要な背景を省かない。対象範囲の修正と検証を行わせ、実装理由のうちコードから自明でないものは日本語コメントで説明させる。
3. 2回目以降の修正は、保持したagent IDへの`collaboration.followup_task`で指摘・根拠・回答を渡す。別の修正agentに交代しない。指摘が誤りと思われる場合は根拠を確認し、未解決のまま無視しない。Gitのコミット・プッシュと確認ファイルの編集は親が担当する。
4. 修正後は新規レビュアーを作って繰り返す。最終変更を含む全差分を新規レビュアーが確認し、指摘ゼロかつ必要な検証が成功した場合だけ完了とする。指摘箇所だけの確認で合格にしない。

指定モデルや`ultra`等の設定が利用できない場合は無断で代替しない。回数上限で合格扱いにしない。判断不能、同じ問題の反復、必要な検証の失敗・実行不能、修正agentの再利用不能などで進められなければ、理由と選択肢を確認ファイルへ記録する。未決定に依存しない作業は進める。

## ユーザー確認

親が確認事項を`/Users/matsuuramiharu/code/review.md`に追記する。既存内容・回答を保持し、確認事項ごとに背景と判断点、未選択のMarkdown checkboxを2つ以上、具体的な選択肢ごとの理由・影響、推奨案、回答欄を設ける。既存の回答が今回の判断を解決していれば再質問しない。

ユーザーにはファイルへのリンクと必要な判断を案内し、回答は待たず保留のまま作業を完了させる。必要な書き込み権限がない場合は権限を得て記録し、確認前に依存する操作を実行しない。

## コミット・プッシュと報告

1. 指摘ゼロと必要な検証の成功後、[git-commit-push](../git-commit-push/SKILL.md)の手順で対象変更だけをコミットし、SSHでプッシュする。コミット予定の差分・送信予定の全コミットを確認し、レビュー済み範囲と一致させる。既存の無関係な変更・履歴が混ざる場合は勝手に送らず確認する。
2. フックなどでレビュー後に内容が変わったら、変更後の全差分についてレビューと検証をやり直してから送信する。
3. 変更内容、検証結果、レビューの完了、コミットSHA、送信先、関連リポジトリへの影響と未実施事項を簡潔に報告する。PRは作成しない。
