# 仕様書レビュー

実装とテストの判断基準にできる仕様かを評価する。このスキルはレビュー観点と判定方法を定める。単独利用では対象の仕様・実装を変更せず、修正・コミット等は別途の依頼や呼び出し元ワークフローの範囲に従う。

## 対象と参照元

1. 対象サービス、文書、機能、対象版、変更差分、レビューの目的を確認する。差分レビューでは変更箇所に加え、影響する既存仕様と関連領域の契約を読む。全体レビューと差分レビューの確認範囲を区別する。
2. 適用される`AGENTS.md`と、参照可能な同サービスの`{{サービス名}}_docs`内の上位要件、用語集、画面・API・データ設計、テスト設計書を確認する。既存実装がある場合は、関連するfrontend・backend・infrastructure等の公開インターフェースと制約も確認する。
3. 要件・受入条件IDと根拠となるパス・節・版またはコミットを対応付ける。IDがなければレビュー内の追跡用IDを使う。参照できない文書・リポジトリは明示し、確認可能な範囲を進める。
4. 文書間の優先順位と決定済み事項を確認する。実装の現状を仕様の正解にせず、仕様と実装の差が意図した変更か不整合かを根拠から判断する。根拠が足りなければ未決事項とする。

## レビュー観点

各観点を対象の性質とリスクに応じて確認する。非該当には理由を付け、情報不足を非該当として扱わない。表の例を満たすためだけに、対象と無関係な要件を追加要求しない。

| 観点 | 確認する内容 |
| --- | --- |
| 1. 完全性（網羅性） | 対象・対象外、利用者・ロール、前提・制約、主要ユースケース、入力・出力、業務ルール、データとライフサイクルが揃っているか。正常系だけでなく、境界値、空・未設定、異常系、状態遷移、権限差、同時操作、外部依存の失敗、副作用と取消が必要な範囲で定義されているか。 |
| 2. 明確性 | 用語、主語、条件、単位、桁数、範囲・上限下限の包含、日時・タイムゾーン、エラー時の結果が一意に読めるか。「適切に」「高速に」等の曖昧語や、例だけで決まるルールが残っていないか。必須要件、推奨、例、未決事項を区別できるか。 |
| 3. 整合性 | 文書内・文書間・関連リポジトリ間で用語、型、必須項目、API契約、状態遷移、権限、エラー、画面と永続化結果が矛盾しないか。上位要件、図表、サンプル、テスト設計書が同じ版の判断を表しているか。 |
| 4. 妥当性 | 利用者の目的と業務上の問題を解決し、要求の根拠と優先度が説明できるか。技術・外部サービス・体制・予算・期限の制約下で実現可能か。過剰な制約や不要な複雑さがなく、必要な依存先・前提が成立しているか。 |
| 5. テスト可能性 | 各要件に観測可能な受入条件があり、前提・具体的入力・操作・期待結果から合否を決められるか。非機能要件にも測定条件・指標・閾値があるか。要件・受入条件とテストID、単体・結合・ユーザー操作を起点としたE2Eの対応、およびテストデータの準備・後始末を定義できるか。 |
| 6. 追跡可能性・変更管理 | 要件の出所、理由、優先度、依存関係、決定状況を追跡できるか。変更・廃止した要件から影響する仕様、実装、テスト、関連リポジトリを特定できるか。未決事項に判断点と影響範囲があるか。 |
| 7. セキュリティ・プライバシー | 信頼境界、認証・認可、ロール・テナント間の分離、入力やファイルの扱い、秘密情報・個人情報の収集・利用・保持・削除・ログ方針が必要な範囲で定義されているか。監査や適用される法令・契約の要件が出所とともに示されているか。 |
| 8. 性能・拡張性・信頼性 | 想定負荷・データ量、応答時間・処理量、容量・コストの制約、可用性が測定条件とともに定義されているか。タイムアウト、再試行、重複処理、部分失敗、同時実行時の整合性と復旧後の状態が決まっているか。 |
| 9. 運用・障害対応 | 必要な監視、ログ・監査、異常検知、通知先、調査に必要な情報を定義しているか。設定変更、配備、バックアップ・復元、障害復旧、ロールバックの方針と運用責任が明確か。RTO・RPO等の復旧目標は必要性と根拠があるか。 |
| 10. 互換性・移行 | 既存の画面・API・データ・利用者への影響と互換性の方針があるか。スキーマ変更、既存データ移行、新旧版の共存、段階的切替、廃止、移行失敗時の復旧やデータ保全が必要な範囲で定義されているか。 |
| 11. ユーザビリティ・アクセシビリティ | ユーザー向け機能では、主要導線、入力補助、待機・空・エラー状態、誤操作防止と回復手段が定義されているか。対象利用者に応じて、キーボード操作、支援技術、言語・端末等への対応と検証条件が定義されているか。 |

## 確認と指摘の組み立て

- 要件ごとに代表的な正常系と境界・失敗シナリオを当てはめ、複数の実装者が同じ結果を導けるか確認する。状態遷移では遷移条件・禁止遷移・失敗後の状態を、データ更新では更新順序・部分失敗・再実行時の結果も追う。
- 仕様上の不足・矛盾と、任意の改善案を分ける。欠落を指摘する場合は、欠けている情報を必要とする具体的な場面と、判断できない実装・テストを示す。実装方法の好みだけを必須要件にしない。
- 仕様とテスト設計書の期待結果が矛盾する場合は両方の根拠を示す。推測で一方を採用したり、現在の実装に合わせて期待結果を緩めたりせず、決定が必要な箇所を明記する。
- 確認できた事実、根拠からの推論、未確認を区別する。不明な閾値や業務ルールを補完して合格扱いにしない。適用する法令・規格等の要件が不明なら、専門判断が必要な論点として扱う。

## 報告形式

指摘を重要度順にまとめ、同じ原因は統合する。既存の報告様式があればそれを優先し、次を含める。

- 確認範囲：対象文書・版・比較基準、参照した仕様・実装・テスト設計書・関連リポジトリ。
- 指摘：指摘ID、重要度、該当観点、対象のパス・行または節、要件・受入条件ID、根拠、問題が生じる条件と影響、必要な決定・修正案、解消を確認する方法。
- 観点別の結果：「問題なし」「指摘あり」「未確認」「非該当（理由）」と、その根拠。上記の全観点を対象にするが、同じ根拠を重複して記載する必要はない。
- 未決・不足：参照できない資料、判断待ち事項、関連リポジトリへの影響と必要な変更、レビューの限界。

重要度はプロジェクトの定義を優先する。未定義なら、P0は直ちに対処すべき重大な安全性・情報漏えい・データ損失等、P1は主要機能や実装・受入判定を阻む問題、P2は限定条件で不具合や手戻りを生む問題、P3は影響の小さい修正事項とする。発生条件と影響から判断し、任意の改善案は不具合と分ける。テストケースのP0・P1とは用途を区別する。

指摘がない場合も「確認した範囲で指摘なし」とし、未確認・未決の部分を合格や仕様確定として扱わない。
