# 実装前のテスト設計

仕様から期待結果を定め、仕様書とともにアプリ実装の判断基準となり、テストコード生成・実行で正解として使うテスト設計書を作る。このスキルでの設計書作成依頼だけでは、アプリ実装、テストコード生成・実行、コミット・プッシュを行わない。

## 参照元と保存先

1. 対象サービス、今回の開発範囲、適用される`AGENTS.md`を確認する。同じサービス名の`{{サービス名}}_docs`を仕様・設計の参照元とし、関連するfrontend・backend・infrastructure等の公開インターフェース、既存テスト、実行・CI設定も確認する。新規開発で存在しない実装は前提にしない。
2. テスト設計書は必ず仕様書リポジトリ内へ保存する。既存の配置・命名規則を優先し、規則がなければ`{{サービス名}}_docs/test-design/<機能名>.md`に作る。既存設計書が対象を含む場合は重複を作らず更新する。
3. 仕様書リポジトリが特定できない、参照できない、書き込めない場合は保存先・アクセスを確認する。実装リポジトリへの代替保存や、無断でのリポジトリ新設はしない。参照できる仕様の整理など、依存しない作業は進める。

## 仕様から検証可能なケースへ

- 要件と受入条件を列挙し、元の要件IDを維持する。IDがなければ追跡用IDを割り当て、元の仕様のパス・節・版またはコミットを対応付ける。機能要件・非機能要件を含め、対象外には根拠を記す。今回の対象範囲での100%とサービス全体での100%を区別する。
- 不明な挙動は実装や推測で正解にしない。不足・矛盾と影響する要件・ケースを未決事項に記し、該当部分を未確定とする。仕様との整合を取るまでは、その部分を実装可能・設計完了と扱わない。
- 正常、異常、境界値、同値クラス、状態遷移、権限差を仕様に応じて洗い出す。各ケースに安定したテストID、要件・受入条件ID、レベル、前提、具体的な入力・操作、観測可能な期待結果、データ準備・後始末を記す。具体値が仕様で未定なら未決とし、曖昧な「正常に動く」で済ませない。
- 単体は業務ロジック・判定、結合はAPI・DB・コンポーネント間の契約や障害時の整合、E2Eはユーザーの目的達成に割り当てる。各ケースの配置予定リポジトリ・テストファイル・モック境界を明記する。内部の重要な接続をモックしたケースをサービス全体のE2E検証として数えない。
- [設計書テンプレート](assets/test-design-template.md)を読み、対象に合わせて記入する。既存様式がある場合も、テンプレートの追跡情報・測定定義・実行条件は含める。不要な欄は理由付きで非該当とし、未決事項と区別する。

## カバレッジと優先度

| 指標 | 目標と設計時に決めること |
| --- | --- |
| 単体・結合のC0（命令網羅） | 実行された命令数 / 対象の全命令数を100%にする。statement coverage等、使用ツールでの対応指標を記す。行カバレッジだけで代替しない。 |
| 単体・結合のC1（分岐網羅） | 通過した分岐結果数 / 対象の全分岐結果数を100%にする。真偽、switch、例外等をツールの計測仕様に合わせてケースへ対応付ける。条件網羅やMC/DCとは区別する。 |
| Playwright E2EのP0・P1実装率 | 各優先度の実装済みケース数 / 設計済みケース数をそれぞれ100%にする。 |
| Playwright E2EのP0・P1成功率 | 各優先度の成功ケース数 / 設計済みケース数をそれぞれ100%にする。必須ブラウザ・実行構成をすべて満たしたケースのみ成功に数える。 |
| 要件カバレッジ | 単体・結合・E2Eを合わせて100%。要件の全受入条件を検証するケースが揃った要件数 / 対象要件総数で計算し、レベル間の重複を除く。設計時はケースへの割当率、実装後は必要なケースが実装・成功した要件の検証達成率を別々に示す。 |
| Flaky | 全テストで観測されたFlaky件数0を目指す。特にE2Eでは反復実行とretryの結果を残す。 |

- C0・C1はレベル別および単体・結合の合算の測定範囲、計測ツール、対象ファイル、未実行ファイルの収集方法、除外と根拠、実行コマンド、レポート保存先を定める。合算は同一ソース・同一版のカバレッジデータを統合し、割合の加算・平均をしない。レポートがないレベルを100%とみなさない。
- 実装前には分岐候補と必要な入力を設計し、C0・C1の実測値は「未計測」とする。実装後に確定する命令・分岐と実測との差を基に、不足ケースを設計書へ追加する。カバレッジのためだけの期待値のない実行は要件検証に数えない。
- プロジェクトの優先度定義を優先する。未定義ならP0は主要導線の停止、重大なデータ損失、不正アクセス等の致命的影響を検出するケース、P1は主要機能、頻出操作、重要な異常系を検証するケースとし、分類理由を残す。P0・P1はユーザー操作を起点に、目的・操作順・画面の結果・必要な永続化や副作用まで記す。API呼び出しだけではE2Eの代替にしない。
- 未実装、skip、fixme、隔離、期待する失敗扱い、未実行、retryでのみ成功したP0・P1は達成に数えない。分母0は非該当として理由を示し、100%と表示しない。達成率のための要件除外、優先度引下げ、カバレッジ除外をしない。到達不能等の正当な除外も根拠と残る不足を明示する。

## PlaywrightとFlakyの設計

- 再実行可能なPlaywright Testを前提とし、起動方法、baseURL、実サービス間の接続、外部依存の扱い、ブラウザ・端末、認証ロール、CI条件、タイムアウト、report・trace等の保存先を定める。Playwright MCPによる手動確認だけをE2E実装済みと数えない。
- ユーザーが識別できるrole・label等のlocatorと自動待機・再試行するassertionを使う方針にする。固定sleep、壊れやすいDOM構造、実行順序依存を避ける。認証・DB等のテストデータをケース・worker間で分離し、時刻・乱数・非同期完了・外部依存を再現可能にする方法と後始末を決める。
- Flakyは同じコード・条件で成否が揺れるテストとし、初回失敗後のretry成功も含める。判定対象・反復回数・必須構成・並列数・初回成否・retry履歴を記録する方法を決める。既存基準がなければ暫定でP0・P1を各必須構成のCI相当条件・並列数で10回反復し、retryなしで全回成功、観測Flaky 0を判定条件として明記する。他レベルも不安定さが判明したケースの再現条件と検証方法を記す。
- retryは診断用として扱い、成功率を補正しない。利用バージョンが対応する場合は`--fail-on-flaky-tests`等でCIを失敗にし、未対応ならreportでFlakyを判定する方法を計画する。反復結果は観測範囲での根拠であり、将来のFlaky不存在の証明とはしない。

Playwrightの詳細やオプションは対象リポジトリの導入バージョンと[Best Practices](https://playwright.dev/docs/best-practices)、[Assertions](https://playwright.dev/docs/test-assertions)、[Retries](https://playwright.dev/docs/test-retries)、[CLI](https://playwright.dev/docs/test-cli)で確認する。

## 整合確認と引き継ぎ

保存前に、要件・受入条件とテストIDの対応漏れ、ID重複、期待結果の仕様根拠、P0・P1の選定漏れ、測定分母、Flaky判定条件、関連リポジトリ間の契約の整合を確認する。未決・不足があれば草案とし、設計完了や各目標の達成を報告しない。

後続のアプリ実装では、仕様書と最新の整合したテスト設計書を併せて参照し、各ケースの前提・入力・操作・期待結果を満たすように実装する。正常系だけでなく、境界値・異常系・状態遷移・権限・副作用も実装へ反映する。作業を別のagentへ渡す場合も、仕様書とテスト設計書のパス・対象要件・テストID・未決事項を引き継ぐ。

テストコードはテスト設計書を正解として生成・実行し、テストIDをコードや結果と対応付ける。実装の現状に合わせた期待値の緩和、assertion削除、skip等で合格させない。仕様変更・設計漏れは、根拠を基に仕様と設計書を先に整合させてからアプリ実装とテストコードへ反映する。

設計書の保存先、参照した仕様・関連リポジトリ、設計したケースと各目標への対応、整合確認結果、未決事項・後続の関連変更を簡潔に報告する。設計完了と、まだ実施していないテスト実行・実測による目標達成を区別する。
