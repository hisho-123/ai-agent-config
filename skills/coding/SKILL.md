# 実装ワークフロー

## 適用範囲と許可

- 親agentが調整し、実装・修正はGPT-6.1 Solの高、レビューはGPT-6 Astraのウルトラに担当させる。親が指定モデルの作業を代行しない。
- ユーザーが「実装して」などの依頼をした場合、その対象に限りコミット・プッシュ・PR作成までの明示許可を含む。「`$coding`で対象を実装」のように対象を伴ってこのスキルでの作業を明示的に依頼した場合も含め、「一括」という追加の語句の有無だけで再確認しない。得た許可を再確認しない。
- 自動選択は可能だが、自動選択だけ、名前への単なる言及、手順の説明、このスキルの作成・更新依頼は外部操作の許可にしない。その場合は許可済みの作業を進め、未許可の操作が必要になった時点で下記の確認方法を使う。
- 無関係な既存変更・コミットを取り込み、送信はしない。履歴書き換え、force push、PRのマージは含まない。

## 開始時の確認とブランチ

1. 対象リポジトリの`AGENTS.md`、仕様、検証方法、Git状態、リモート、既存のステージ済み・未ステージ・未追跡ファイルを確認する。参照可能な同サービスの`{{サービス名}}_docs`と関連領域の実装を確認し、必要な関連変更を作業対象に含める。
2. 開始時のHEAD、変更内容とステージ状態を記録し、既存のユーザー変更は未追跡ファイルも含めてstashにより保護する。作成したstashのSHAと退避内容を記録し、このワークフローでは復元・削除せず保持する。勝手なreset、cleanや既存変更の上書きをしない。安全に進められない部分は確認事項とする。
3. ブランチ指定があればそれを尊重する。未指定なら現在のブランチを使い、現在が`main`の場合だけ、対応するリモートを取得して`main`をfast-forwardのみで最新化し、新規ブランチを作る。未コミット変更で安全な更新・切り替えができない場合や、履歴が分岐している場合は停止して確認する。detached HEADは対象ブランチを確認する。
4. 新規ブランチ名は内容を表す英単語2つをハイフンでつなぎ、`codex/feature-name`形式を推奨する。`codex/`は2語に数えない。指定済みのブランチ名は改名しない。既存の同名ブランチを上書きしない。
5. レビューの比較先はユーザー指定を優先し、なければPRのマージ先となるデフォルトブランチとする。取得した比較先と作業ブランチのmerge-baseのSHAを固定する。最新化した`main`から作る場合は分岐時のSHAを固定する。以後の反復でbaseを動かさない。比較先を確定できなければ確認する。

## 実装agent

`collaboration.spawn_agent`で次の値を指定し、返されたagent IDを最後の修正まで保持する。

```text
task_name: coding_implementation
model: gpt-6.1-sol
reasoning_effort: high
fork_turns: none
```

`message`には依頼内容、対象リポジトリの絶対パス、適用指示・関連仕様、ブランチ、固定base SHA、開始時の変更と保護対象、検証方法、確認済みの回答を明示的に渡す。履歴は引き継がれないため、必要な背景を省かない。実装理由のうちコードから自明でないものは日本語コメントで説明させる。

実装agentに対象範囲の実装と必要な検証を行わせ、変更内容・結果・残件を受け取る。Gitのコミット・プッシュ・PR作成とユーザー確認ファイルの編集は親が担当する。指定モデルや`ultra`等の設定が利用できない場合は無断で代替せず、確認事項にする。

## レビューと修正の反復

1. 初回を含む各回で、新しい`task_name`のレビュアーを`collaboration.spawn_agent`で作る。`model: gpt-6-astra`、`reasoning_effort: ultra`、`fork_turns: none`を必ず指定する。
2. レビュアーには依頼、仕様・指示、絶対パス、固定base SHA、確認済みの回答、検証方法を渡す。前回レビューの結論や修正者の「解決済み」判断は渡さず、最新の実装と差分から独立して判定させる。
3. レビューは読み取り専用とする。固定baseからHEADまでのコミット済み変更、ステージ済み変更、未ステージ変更、未追跡ファイルをすべて対象にし、削除・名前変更も確認させる。`git diff <固定base>`だけでは未追跡ファイルが入らないため、`git ls-files --others --exclude-standard`等で列挙して内容も確認する。
4. 仕様違反や具体的な不具合について、重要度、ファイルパスと行、再現条件・根拠、必要な検証を報告させる。好みだけの指摘を不具合に数えない。指摘がない場合も、確認範囲と検証結果・未実施事項を明示させる。
5. 指摘があれば親が整理し、保持した実装agent IDに`collaboration.followup_task`で指摘と根拠、確認済みの回答を渡して修正・検証させる。別の修正agentに交代しない。指摘が誤りと思われる場合は根拠を確認し、未解決のまま無視しない。
6. 修正後は別の新規レビュアーで繰り返す。最終変更を含む全差分を新規レビュアーが確認し、指摘ゼロかつ必要な検証が成功した場合だけ完了とする。指摘箇所だけの確認で合格にしない。

回数上限で合格扱いにしない。判断不能、同じ問題の反復、必要な検証の失敗・実行不能、修正agentの再利用不能などで進められなければ、理由と選択肢を確認ファイルへ記録する。未決定に依存しない作業は進める。

## ユーザー確認

親が確認事項を`/Users/matsuuramiharu/code/coding.md`に追記する。既存内容・回答を保持し、確認事項ごとに背景と判断点、未選択のMarkdown checkboxを2つ以上、具体的な選択肢ごとの理由・影響、推奨案、回答欄を設ける。既存の回答が今回の判断を解決していれば再質問しない。

ユーザーには最後にファイルへのリンクと必要な判断を案内し、回答は待たず保留のまま作業を完了させる。必要な書き込み権限がない場合は権限を得て記録し、確認前に依存する操作を実行しない。

## コミット・プッシュ・PR

1. 指摘ゼロと必要な検証の成功後、[git-commit-push](../git-commit-push/SKILL.md)の手順で対象変更だけをコミットし、SSHでプッシュする。コミット予定の差分の全コミットを確認し、レビュー済み範囲と一致させる。
2. 送信先リポジトリ・ブランチと送信済みSHAの確認結果を[github-pr-create](../github-pr-create/SKILL.md)へ引き継ぐ。PRのマージ先リポジトリと送信先を区別して既存PRを確認し、同スキルの`--repo`・`--base`・`--head`を明示する手順で日本語のPRを作成する。URL指定プッシュではupstream・リモート追跡参照の更新を前提にしない。追加プッシュが必要になった場合も`git-commit-push`の確認・SSH手順を使う。
3. フックなどでレビュー後に内容が変わったら、変更後の全差分についてレビューと検証をやり直してから送信する。
4. 変更内容、検証結果、レビューの完了、コミットSHA、送信先、PRのURL、関連リポジトリへの影響と未実施事項を簡潔に報告する。stashした場合は、完了・保留・失敗のいずれの報告にも、stashした事実・SHA・退避内容と、復元せず保持していることを含める。
