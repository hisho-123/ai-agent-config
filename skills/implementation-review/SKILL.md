# 実装レビュー

仕様とテスト設計書を基準に、実際の不具合とリスクを根拠付きで評価する。このスキルはレビュー観点と判定方法を定める。単独利用では対象の実装・仕様を変更せず、修正・コミット等は別途の依頼や呼び出し元ワークフローの範囲に従う。

## 対象と判断基準

1. 適用される`AGENTS.md`、対象機能・ブランチ・版、レビュー範囲を確認する。呼び出し元が固定した比較先SHAと対象範囲を優先する。比較先を決められない場合は推測せず、確認可能な範囲と制約を明示する。
2. 同サービスの参照可能な`{{サービス名}}_docs`内の仕様書・テスト設計書と、関連するfrontend・backend・infrastructure等の実装・契約・CI設定を読む。仕様・受入条件ID、テストID、実装箇所、検証結果の対応を追う。参照できないものは未確認とする。
3. コミット済み差分に加えて、対象に含まれるステージ済み・未ステージ変更、未追跡ファイル、削除・名前変更を確認する。`git diff <固定base>`だけでは未追跡ファイルを確認できないため、`git ls-files --others --exclude-standard`等で列挙して内容を読む。
4. 差分だけで結論を出さず、呼び出し元・呼び出し先、データ定義、関連テスト、設定、既存利用箇所まで確認する。変更起因の問題と、今回の変更に依存しない既存問題を区別する。依頼が全体レビューなら既存問題も対象にする。
5. 仕様に合う期待結果をテスト設計書で確認する。仕様・設計書がない、未確定、相互に矛盾する場合は、その不足と影響する要件・テストIDを報告し、該当部分の仕様準拠を合格扱いにしない。資料の整備が必要でも、コードから確認できる不具合のレビューは進める。

## レビュー観点

各観点を対象の性質とリスクに応じて確認する。非該当には理由を付け、情報不足を非該当として扱わない。プロジェクトの要件を超える設計変更や、一律の技術導入を要求しない。

| 観点 | 確認する内容 |
| --- | --- |
| 1. 仕様準拠 | 要件・受入条件とテスト設計書の前提・入力・操作・期待結果を満たすか。正常系、境界値、異常系、状態遷移、ロール・権限差、副作用、対象外の扱いに漏れがないか。画面・API・DB・関連リポジトリで同じ契約を実装しているか。 |
| 2. 正確性 | 条件分岐、計算、型変換、null・空値、範囲の端、丸め・精度、日時・タイムゾーンが正しいか。非同期の完了順、競合、再実行、例外、リソース解放、キャンセルを含めて期待どおりの結果になるか。 |
| 3. 設計・アーキテクチャ | 既存の責務分担・レイヤー・依存方向に合うか。契約や業務ルールが適切な境界で保証され、循環依存、不要な密結合、過剰な抽象化がないか。外部サービス・環境設定との境界、変更の局所性、テストのしやすさが保たれるか。 |
| 4. データ整合 | スキーマ・制約・トランザクションの範囲が不変条件を守るか。同時更新、ロック、重複要求、冪等性、部分失敗、イベント順序、キャッシュ整合、削除・参照整合を扱えるか。再試行や補償後も欠落・二重更新がなく、データ移行が既存データを保全するか。 |
| 5. 保守性・可読性 | 命名、責務、複雑さ、重複、型・エラーの扱いが変更を誤らせないか。既存規約に沿い、不要な変更・死んだコードがないか。コードから自明でない実装理由や制約が日本語コメント等で説明されているか。好みだけの書式・命名差を不具合にしない。 |
| 6. テスト品質 | 要件・受入条件とテストIDが追跡でき、仕様に根拠のある期待結果をassertしているか。正常・異常・境界・状態遷移・権限・副作用を適切な単体・結合・E2Eで検証し、モックが検証対象の欠陥を隠していないか。テストデータ・後始末・独立性・再現性・カバレッジの測定が適切か。 |
| 7. セキュリティ・プライバシー | 認証・認可を信頼できる境界で実施し、オブジェクト・テナント単位の権限を守るか。入力検証、出力処理、SQL・コマンド・URL・ファイルの扱いに悪用可能な経路がないか。秘密情報・個人情報の露出、過剰な保持、ログ・エラーへの混入、依存関係の既知の問題が変更に関係しないか。 |
| 8. 性能・拡張性 | 想定負荷で仕様上の応答時間・処理量・容量を満たすか。N+1、索引不足、無制限の取得・ループ・キュー、メモリ増加、接続枯渇、外部呼び出しの増幅がないか。ページング、上限、キャッシュ等は整合性・コストとの両面で妥当か。 |
| 9. 信頼性・障害対応 | タイムアウト、再試行の回数・間隔、冪等性、部分失敗、取消、復旧時の状態が仕様に合うか。例外の握り潰し、誤った成功応答、無限再試行がないか。外部依存の障害や負荷増大でも、必要な機能とデータを保護できるか。 |
| 10. 互換性・回帰・移行 | 既存の呼び出し元、API、保存データ、設定、対応環境への破壊的影響がないか。新旧版の共存、スキーマ適用順、既存データ移行、再実行、切替・ロールバックを扱えるか。削除・名前変更、依存更新、生成物、関連リポジトリの変更漏れを確認したか。 |
| 11. 運用・可観測性・配備 | 必要なログ、メトリクス、トレース、監査、アラートで失敗と影響を特定できるか。ログに必要な識別情報があり、機密情報を含まないか。環境変数・秘密情報、ヘルスチェック、CI/CD、配備・復旧手順、運用文書が変更と整合するか。 |
| 12. ユーザビリティ・アクセシビリティ | UI変更では、操作導線、ローディング・空・エラー状態、二重送信防止、入力保持、誤操作からの回復が仕様を満たすか。対象環境でキーボード、フォーカス、ラベル、支援技術、表示サイズ・言語等への対応を損なっていないか。 |

## 検証方法

- 指摘候補ごとに、実際の制御・データの流れを追い、入力・前提・操作と誤った結果を特定する。既存のガード、呼び出し条件、フレームワークの保証、関連テストで問題が防がれていないかを確認してから指摘する。
- リスクに合う既存の静的検査・型検査・単体・結合・E2Eを、許可された検証環境で実行する。必要なら対象のソースを変更しない最小再現を一時領域に作る。本番データの更新や外部への送信を伴う検証は、通常のローカル検証と同じ許可とみなさない。
- コマンド、対象版、環境・構成、結果とレポートを記録する。実行していない検証は未実施とし、コードを読んだ推定と実測を分ける。テスト成功だけで、未検証の要件や非機能要件まで満たしたと判断しない。
- テスト設計書の目標と実測を照合する。単体・結合のC0（命令網羅）・C1（分岐網羅）各100%、Playwright TestによるE2EのP0・P1それぞれ100%実装・成功、全レベルを合わせた要件カバレッジ100%、観測Flaky 0を目指す。レベル別と合算、測定対象・分母・除外理由を確認し、割合の平均や行カバレッジだけでC0・C1を代替しない。
- skip・隔離・未実行・retryでのみ成功したケースを達成に数えない。分母0は理由付きで非該当とする。Flaky 0には観測した版・構成・並列数・反復回数・初回成否・retry履歴を添え、1回成功しただけで不安定さがないと断定しない。測定条件が設計書で未定なら、その不足を報告する。
- 期待値の緩和、assertion削除、skipやretryによる見かけの合格を解決としない。仕様変更や設計漏れは、根拠に基づいて仕様書・テスト設計書を先に整合させる必要を示す。

## 報告形式

指摘を重要度順にまとめ、同じ原因は統合する。既存の報告様式があればそれを優先し、次を含める。

- 確認範囲：対象版・固定base・差分範囲、参照した仕様書・テスト設計書・関連リポジトリ。
- 指摘：指摘ID、重要度、該当観点、対象のパスと最小限の行範囲、関連要件・テストID、発生条件、期待結果と実際の挙動、根拠、影響、修正方針、必要な検証。可能なら再現コマンドや失敗したテストを示す。
- 観点別の結果：「問題なし」「指摘あり」「未確認」「非該当（理由）」と、その根拠。上記の全観点を対象にするが、同じ根拠を重複して記載する必要はない。
- 検証結果：実行コマンドと成否、カバレッジの範囲・分母・除外、E2Eと要件の達成状況、Flakyの観測条件、未実施・実行不能事項。
- 残件：仕様の未決事項、関連リポジトリへの影響と必要な変更、既存問題・任意の改善案、レビューの限界。

重要度はプロジェクトの定義を優先する。未定義なら、P0は直ちに対処すべき重大な安全性・情報漏えい・データ損失等、P1は主要機能の停止や重大な仕様違反、P2は限定条件で起きる具体的な不具合、P3は影響の小さい修正事項とする。発生条件と影響から判断し、好みや根拠のない懸念を不具合として数えない。テストケースのP0・P1とは用途を区別する。

指摘がない場合も「確認した範囲で指摘なし」とする。必要な検証の失敗・未実施や仕様の未確定が残る場合は、それを解消した、あるいは品質目標を達成したと報告しない。
