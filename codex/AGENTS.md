# 共通指示

- ユーザーが別の言語を指定しない限り、日本語で回答する。
- 結論と必要な根拠を簡潔に説明する。
- ファイルや設定を変更した場合、変更内容と検証結果を報告する。
- コード実装の際には、実装根拠・理由をコメントで明示する（日本語）。コードから理解できる内容は記載しない。

# リポジトリ命名ルール

- リポジトリ名は `{{サービス名}}_{{領域}}` とする。
- 同じサービスのリポジトリでは、サービス名を統一する。
- 領域は以下を例とし、必要に応じて追加する。

| 領域 | 役割 |
| --- | --- |
| `docs` | サービス全体の仕様・設計 |
| `frontend` | 画面・フロントエンド実装 |
| `backend` | API・バックエンド実装 |
| `infrastructure` | インフラ構成・環境管理 |

# サービス全体の仕様・実装の管理

- 同じサービス名を持つリポジトリを、サービス全体を構成する関連リポジトリとして扱う。
- 作業時は、参照可能な `{{サービス名}}_docs` を仕様・設計の参照元とし、関連する領域の実装も確認する。
- 仕様・実装を変更する際は、関連リポジトリへの影響と、仕様・実装間および領域間の不整合を確認する。
- 必要な関連変更を把握し、変更内容とあわせて報告する。

# テスト設計書に基づく実装・検証

- アプリの実装前に、同じサービスの仕様書リポジトリ `{{サービス名}}_docs` 内へテスト設計書を作成・更新する。既存の配置規則を優先し、未定なら `test-design/<機能名>.md` とする。`test-design` skillが利用可能なら使用する。
- アプリの実装時は、仕様書とテスト設計書を併せて参照し、各ケースの前提・入力・操作・期待結果を満たすように実装する。正常系に加え、境界値・異常系・状態遷移・権限・副作用も実装へ反映する。
- テスト設計書を期待結果の正解として、単体・結合・E2Eのテストコードを生成・実行する。テストIDで要件・受入条件、コード、実行結果を対応付ける。設計書が未作成・未確定なら、先に整備する。
- 単体・結合テストはC0（命令網羅）・C1（分岐網羅）の各100%を目指す。E2EはPlaywright Testでユーザー操作を起点に設計し、P0・P1それぞれの100%実装・成功を目指す。要件カバレッジは単体・結合・E2Eを合わせて100%、Flakyテストは0を目指す。
- 実装の現状に合わせて期待値を緩めず、仕様変更や設計漏れは根拠を基に仕様書とテスト設計書を先に整合させてからアプリ実装とテストコードへ反映する。不明・矛盾は未決事項として報告し、該当部分を合格扱いにしない。
- skip・隔離・retryでのみ成功したケースを目標達成に数えず、カバレッジの対象・分母・除外理由、実行結果、Flakyの観測条件、未達・未実施事項を報告する。
